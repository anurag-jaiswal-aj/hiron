# Phase 8 Step 2 — Scoring Domain Contract

## 1. Existing Domain Model
The scoring domain evaluates a `Candidate` against a `Job` to produce a quantitative and qualitative assessment of fit. The engine takes in raw candidate/job data, calculates a `fit_score` (0-100), a `confidence` metric (0.0-1.0), and a detailed dimensional `breakdown` with an overarching `explanation`.

## 2. Database Contract
The `scores` table requires the following persisted fields:
- **Foreign Keys**: `tenant_id`, `job_candidate_id`
- **Scores**: `fit_score` (SmallInteger, 0-100), `confidence` (Float, 0.0-1.0)
- **Qualitative Data**: `breakdown` (JSONB), `explanation` (Text)
- **Skills Gap**: `skills_matched` (JSONB list of strings), `skills_missing` (JSONB list of strings)
- **Safety/Checks**: `warnings` (JSONB list of strings)
- **Provenance / Telemetry**: `prompt_name`, `prompt_version`, `model_version`, `input_tokens` (>= 0), `output_tokens` (>= 0), `latency_ms` (>= 0)
- **State**: `is_current` (Boolean), `created_at` (DateTime)

## 3. API Contract
The `ScoreResponse` returns a `ScoreData` object.
The `ScoreHistoryResponse` returns `ScoreHistoryItem` objects (a subset of `ScoreData`).
The `ScoreExplanationResponse` returns `ScoreExplanationData` (which adds `confidence_factors`).

## 4. ScoreData Contract
`ScoreData` exposes the following to the client:
`id`, `fitScore`, `confidence`, `breakdown`, `explanation`, `skillsMatched`, `skillsMissing`, `warnings`, `promptVersion`, `modelVersion`, `isCurrent`, `createdAt`.

## 5. ScoreBreakdown Contract
The `ScoreBreakdown` schema mandates exactly three dimensions:
1. `skills`
2. `experience`
3. `education`

Each dimension is represented by a `BreakdownDimension` schema containing:
- `score`: int (assumed 0-100 based on mock logic)
- `weight`: float (e.g., 0.40, 0.35, 0.25)
- `details`: str (textual explanation of the dimensional score)

## 6. AI-Generated Fields
Based on the objective of LLM evaluation with structured output, Gemini is responsible for generating the qualitative analysis and the base scores.
- `explanation`
- `breakdown` (and the `details` and `score` within each dimension)
- `skills_matched`
- `skills_missing`
- `fit_score` (Subject to application-level vector similarity rules, see Section 8)
- `confidence` (Subject to application-level vector similarity rules, see Section 8)

## 7. Application-Derived Fields
The following fields MUST be generated by the application, not the LLM:
- **Telemetry**: `input_tokens`, `output_tokens`, `latency_ms`
- **Provenance**: `prompt_name`, `prompt_version`, `model_version`
- **Safety**: `warnings` (In the mock, `run_hallucination_and_consistency_checks` computes these based on the AI's output).
- **Metadata**: `id`, `tenant_id`, `job_candidate_id`, `is_current`, `created_at`

## 8. Vector Similarity Contract
The existing mock calculates `cos_sim` between `candidate_vector` and `job_vector`.
- It applies `vector_boost = (cos_sim - 0.5) * 10` to the weighted dimensional score to produce the final `fit_score`.
- It applies `(cos_sim * 0.25)` to the `confidence`.
**Ambiguity**: It is NOT ESTABLISHED BY CURRENT CODEBASE whether this vector manipulation is an intentional product rule for a hybrid search architecture, or merely a naive formula used exclusively to make the mock engine behave dynamically. Currently, the vector similarity is NOT passed into the `PromptBuilder`.

## 9. Candidate Input Contract
Passed to `PromptBuilder`:
- `candidate_skills` (Comma-separated string)
- `candidate_summary` (String)
- `candidate_resume_text` (String)

## 10. Job Input Contract
Passed to `PromptBuilder`:
- `job_description` (String)
- `job_required_skills` (Comma-separated string)

## 11. PromptBuilder Contract
`PromptBuilder.build_messages()` outputs a strict two-message array (for OpenAI compatibility, which Gemini accepts via some adapters, though Gemini natively uses `contents` with `parts`):
1. `{"role": "system", "content": "{system_instructions} + SECURITY DIRECTIVE..."}`
2. `{"role": "user", "content": "<label>\n{truncated_content}\n</label>..."}`
The prompt injection protections (truncation, secondary signal detection, and XML encapsulation) MUST remain unchanged.

## 12. Response Mapping Contract
The JSON output from Gemini must be mapped back into the dictionary structure expected by `ScoreService`, merging the AI's qualitative output with the application's telemetry and provenance data before being passed to `ScoreRepository.create_score()`.

## 13. Validation Rules
- `fit_score` must be 0-100.
- `confidence` must be 0.0-1.0.
- `tokens` and `latency_ms` must be >= 0.

## 14. Existing Test Requirements
- `test_scoring_engine.py`: Contains tests like `test_cosine_similarity_calculation` and `test_scoring_engine_full_evaluation` which strictly assert the exact mathematical outputs of the mock heuristic. These tests only validate the heuristic mock and MUST be changed.
- `test_score_service.py` / `test_scores_api.py` / `test_scores_webhook.py`: Represent true product requirements (routing, DB persistence, QStash worker flows, RBAC) but will require HTTP mocks once the engine makes real network calls.

## 15. Contradictions / Ambiguities
- **Prompt Format**: `PromptBuilder` outputs `[{"role": "system"}, {"role": "user"}]`. The Gemini REST API natively expects a `contents` array and an optional `systemInstruction`. The engine must map the OpenAI-style message format to the Gemini REST payload.
- **Vector Integration**: If the LLM generates the `fit_score`, does the application still apply the `vector_boost`? NOT ESTABLISHED BY CURRENT CODEBASE.

## 16. Decisions Required Before Implementation
1. **Vector Boost**: Should the application apply the vector boost to the LLM's `fit_score` output, or discard the vector boost entirely since the LLM has full semantic understanding of the text?
2. **Confidence Metric**: Should the LLM generate the `confidence` metric, or should it remain a mathematical derivation of the vector similarity?
3. **Warnings Logic**: The mock engine runs `run_hallucination_and_consistency_checks` post-generation. Should this remain an application-level check?

## 17. Recommended Gemini Output Schema
Based on the `ScoreData` and `ScoreBreakdown` schemas required by the API and Database, the LLM must generate the following JSON.

*Note: All fields below are explicitly derived from existing Pydantic schemas or Database models in the repository.*

```python
from pydantic import BaseModel, Field

class BreakdownDimensionAI(BaseModel):
    score: int = Field(..., description="0-100 score for this dimension")
    details: str = Field(..., description="Explanation for this dimensional score")
    # Note: `weight` is defined in `BreakdownDimension` but is constant in the mock (0.40, 0.35, 0.25). 
    # It is recommended to let the application apply weights rather than asking the LLM to hallucinate them.

class ScoreBreakdownAI(BaseModel):
    skills: BreakdownDimensionAI
    experience: BreakdownDimensionAI
    education: BreakdownDimensionAI

class AIGeneratedScore(BaseModel):
    fit_score: int = Field(..., description="Overall fit score from 0 to 100")
    confidence: float = Field(..., description="Confidence in the evaluation from 0.0 to 1.0")
    explanation: str = Field(..., description="Overall summary explanation of candidate fit")
    skills_matched: list[str] = Field(..., description="List of job required skills the candidate possesses")
    skills_missing: list[str] = Field(..., description="List of job required skills the candidate lacks")
    breakdown: ScoreBreakdownAI
```

## 18. Acceptance Criteria
- Engine validates the LLM response against `AIGeneratedScore`.
- The parsed response is merged with application-derived metadata (telemetry, weights, warnings).
- The final payload perfectly satisfies `ScoreRepository.create_score()` constraints.
