# Phase 21.6.7 Implementation Plan: Batch Coordinator & Fan-Out

## 1. Goal Description
Implement the Coordinator webhook and Database tracking to replace Celery's synchronous long-running batch job `execute_batch_scoring` with an event-driven QStash fan-out architecture.

## 2. Issue 1 — Counter Idempotency
A QStash webhook may be delivered multiple times. To satisfy the invariant that **ONE batch + ONE candidate + ONE logical scoring operation must produce AT MOST ONE terminal counter transition**, we will rely on PostgreSQL array capabilities rather than a complex junction table.

- **Completion Claiming**: When a worker successfully finishes (or encounters an identifiable terminal failure), it MUST execute the candidate terminal claim, counter increment, candidate-ID array update, and `BatchScoreJob` status transition inside the SAME database transaction using existing SQLAlchemy transaction conventions.
- **Atomic Conditional Terminal Claim + State Transition**:
  The required conceptual transaction is:
  ```python
  BEGIN
    # Attempt conditional candidate claim and counter update in one statement
    conditionally claim candidate terminal state
    
    IF this transaction successfully claimed the candidate (rowcount == 1):
        increment completed_count OR failed_count
        append candidate_id to the appropriate array
        recompute BatchScoreJob status based on updated counters
        persist the new status
  COMMIT
  ```
  *   **`rowcount == 1`** => This delivery successfully claimed the candidate's terminal transition. The counters and status state machine are subsequently processed within the same transaction lock, ensuring concurrent workers cannot incorrectly derive the final batch state.
  *   **`rowcount == 0`** => Another delivery already claimed the candidate. The transaction does not modify counters or arrays and safely acknowledges the duplicate delivery.
- **Worker Crash**: If the worker crashes after score generation but before the transaction completes, QStash retries. The second attempt fetches the cached score (no AI API call) and then successfully executes the conditional claim exactly once.

### Design Note: Array Scalability Trade-off
- Array-based candidate tracking is intentionally chosen for Phase 21.6.7.
- It avoids introducing a separate batch-candidate state table.
- It provides atomic duplicate protection for the expected batch size.
- Large batch scalability must be evaluated before using this representation for very large candidate sets because array updates rewrite the `BatchScoreJob` row.

## 3. Issue 2 — Alembic Migration Safety
Autogenerated migrations are NOT implicitly trusted. The implementation will explicitly follow this sequence:
1. Define the `BatchScoreJob` model in `hiron.scores.models`.
2. Generate the migration using `alembic revision --autogenerate`.
3. **STOP** and manually inspect the generated migration file.
4. Verify upgrade/downgrade operations, constraint bindings, and indexes.
5. Apply the migration using `alembic upgrade head`.
6. Verify the schema via PostgreSQL shell or test execution.
7. Run the relevant tests.

## 4. Issue 3 — Batch State Machine
The batch state transitions are strictly defined:
- **Initial/Queued State:** `status = "pending"`, counters = 0. (Created by `batch_score_async`).
- **Running State:** `status = "processing"`. Set by the Coordinator webhook immediately before it begins fan-out publishing. This transition (`pending` -> `processing`) MUST be an atomic conditional claim using SQLAlchemy transaction conventions to ensure concurrent Coordinator deliveries cannot overwrite each other or regress terminal states.
- **Completion Condition:** After ANY successful or terminal candidate conditional claim, the database evaluates the state. The terminal state is explicitly evaluated using the following semantics:
  ```python
  if completed_count + failed_count < queued_count:
      status = "processing"
  elif failed_count == queued_count:
      status = "failed"
  elif completed_count + failed_count == queued_count:
      status = "completed"
  ```
- **Retryable Candidate Failure:** (Gemini 429, Gemini 5xx, transient QStash/API failure). The worker returns HTTP 429 or 503. QStash retries. The database is NOT updated (counters remain unchanged, candidate is not appended to any array).

## 4.1 Coordinator Delivery Idempotency & Atomic State Check
QStash deduplication IDs protect duplicate enqueue operations, but the Coordinator must handle duplicate deliveries correctly at the application level.
The Coordinator reads and claims the `BatchScoreJob` state atomically.
1. **FIRST EXECUTION**: `BatchScoreJob` is `pending`. The Coordinator establishes `queued_count` exactly once, transitions `pending -> processing`, and publishes deterministic worker messages.
2. **RETRY AFTER PARTIAL FAN-OUT**: `BatchScoreJob` is already `processing`. The Coordinator MUST NOT reset `completed_count` or `failed_count`, MUST NOT regress the status, and MUST NOT create a new batch. It republishes the deterministic worker message set, relies on worker deduplication IDs for already-published candidates, and publishes any messages that were not successfully accepted previously.
3. **DUPLICATE AFTER TERMINAL STATE**: If `BatchScoreJob` is `completed` or `failed`, the Coordinator MUST NOT transition it back to `processing`. It acknowledges the duplicate Coordinator delivery with `HTTP 200 OK` and performs NO additional fan-out.

## 5. Unidentifiable Terminal Errors
We must explicitly distinguish between Identifiable and Unidentifiable terminal errors:
- **Identifiable Terminal Error**: (e.g., valid `batch_id` & `candidate_id`, but candidate not found, or domain AI parsing failure). 
  *   **Action**: Atomically claim candidate terminal state, append `candidate_id` to `failed_candidate_ids`, increment `failed_count` exactly once, and return `200 OK`.
- **Unidentifiable Terminal Error**: (e.g., malformed JSON payload missing `batch_id` or `candidate_id`, invalid UUID string format).
  *   **Action**: Return `200 OK` (so QStash drops the message instead of endless retries, per `ERROR_MATRIX.md`), but **DO NOT** fabricate a candidate/batch identity and **DO NOT** attempt a DB counter update. 
  *   **Impact**: If a candidate payload is unidentifiable, `completed_count + failed_count` will never reach `queued_count`. The `BatchScoreJob` will be permanently stuck in `processing`. A periodic timeout/cleanup cron job is required in the future to sweep stale processing batches.

## 6. Partial Fan-Out & QStash Deduplication
The Coordinator's fan-out loop is **NOT transactional**.
If the Coordinator successfully publishes Candidates A, B, and C, but crashes while publishing Candidate D:
1. Candidates A, B, C remain enqueued in QStash.
2. The Coordinator returns 500, prompting a full QStash retry of the Coordinator webhook.
3. The Coordinator retries and attempts to publish the full deterministic set (A, B, C, D) again.
4. **QStash Deduplication Behavior:** Because every publish attempt for Candidate A uses the deterministic `Upstash-Deduplication-Id: batch-worker-{tenant_id}-{job_id}-{candidate_id}-{batch_id}`, QStash duplicate publication is handled according to QStash deduplication semantics (the API drops the duplicate within the deduplication window).
5. Candidate D is successfully enqueued.
This design makes non-transactional HTTP loop publishing completely safe.

## 7. Batch Score Job Schema
Consistent with existing conventions (e.g., `Job.status`), the schema will use `String(20)` and `CheckConstraint` instead of native Postgres ENUM types.
- `id`: `UUID` (Primary Key, default `uuid.uuid4`)
- `tenant_id`: `UUID` (ForeignKey to `tenants.id`, `ondelete="CASCADE"`, indexed)
- `job_id`: `UUID` (ForeignKey to `jobs.id`, `ondelete="CASCADE"`, indexed)
- `status`: `String(20)` (Default `'pending'`)
- `queued_count`: `Integer` (Default `0`)
- `completed_count`: `Integer` (Default `0`)
- `failed_count`: `Integer` (Default `0`)
- `completed_candidate_ids`: `ARRAY(UUID)` (Default `'{}'`)
- `failed_candidate_ids`: `ARRAY(UUID)` (Default `'{}'`)
- `created_at` / `updated_at`: Handled by `BaseModel` mixins.
- **Constraints:** `CheckConstraint` for `status IN ('pending', 'processing', 'completed', 'failed')`.
- **Indexes:** `tenant_id`, `job_id`.

## 8. Fan-Out Implementation Summary
*   **Who acts as coordinator:** `POST /api/v1/webhooks/qstash/scores/batch/coordinator`.
*   **What starts the coordinator:** `ScoreService.batch_score_async` (publishes exactly 1 message to the coordinator).
*   **Candidate Set Stability:** `ONE batch_id = ONE immutable candidate set`. 
    *   `ScoreService.batch_score_async` determines the complete `candidate_ids` list *before* publishing the Coordinator message.
    *   If the user-provided list is empty, `ScoreService.batch_score_async` queries `CandidateRepository.list_job_candidates` to discover the list and embeds it in the payload.
    *   The Coordinator payload always carries the exact `candidate_ids` snapshot.
    *   The Coordinator NEVER re-queries the database on retry, ensuring the exact same candidate list is used on every delivery.
*   **Zero-Candidate Batch Behavior:** If the established candidate snapshot contains zero candidates, the terminal behavior is explicitly defined:
    *   `queued_count = 0`
    *   `completed_count = 0`
    *   `failed_count = 0`
    *   `status = "completed"`
    The Coordinator immediately acknowledges the request with `HTTP 200 OK` and does NOT publish any worker messages.
*   **Exact worker payload:** `{"batch_id": "...", "tenant_id": "...", "job_id": "...", "candidate_id": "...", "force_rescore": false}`
*   **Deduplication IDs:**
    *   Coordinator: `batch-coord-{tenant_id}-{job_id}-{batch_id}`
    *   Worker: `batch-worker-{tenant_id}-{job_id}-{candidate_id}-{batch_id}`
