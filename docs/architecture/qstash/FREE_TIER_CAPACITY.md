# Phase 21.6 QStash Free-Tier Capacity Analysis

## Free-Tier Constraints
Upstash QStash offers a free tier with the following strict limits:
- **Max Messages Per Day:** 1,000
- **Max Payload Size:** 1 MB
- **Retries:** Every retry attempt counts as a separate message against the daily quota.

## Worst-Case Usage Scenario (Daily Activity)

Let's model a high-activity day for a single tenant:
- **Resume Uploads:** 100
- **Candidate Embeddings:** 100 (auto-triggered by uploads)
- **Job Creations/Updates:** 20
- **Batch Scoring:** 1 batch involving 100 candidates

### Base Logical Tasks (Initial Attempt)
1. 100 Resumes = 100 logical messages (`parse_resume`)
2. 100 Candidate Embeddings = 100 logical messages (`generate_candidate_embedding`)
3. 20 Job Embeddings = 20 logical messages (`generate_job_embedding`)
4. 1 Batch Coordinator + 100 Candidate Score Workers = 101 logical messages (`batch_score` fan-out)

**Total Initial Attempts:** 321 delivery attempts

### Worst-Case Retry Storm
Assume the Gemini API aggressively rate-limits (HTTP 429), resulting in 3 retries per logical message across all AI-dependent tasks. Each retry counts as a separate delivery attempt.

- Initial attempt: 321 delivery attempts
- Retry 1: 321 delivery attempts
- Retry 2: 321 delivery attempts
- Retry 3: 321 delivery attempts

**Total Delivery Attempts:** 1,284 delivery attempts

## Definitions
- **Logical Task/Message:** The singular unit of work generated by the application (e.g., parsing a specific resume).
- **Retry Attempt:** A subsequent execution of a logical task after a failure.
- **Delivery Attempt:** Every single HTTP request QStash makes to our API. The free-tier limit applies to *delivery attempts*.

## Conclusion
Under a worst-case scenario with a 100% failure rate on the first 3 attempts for every single task, the system would consume **1,284 delivery attempts**, exceeding the **1,000 delivery attempts** daily free tier limit.

*Note:* According to QStash pricing documentation, the 1,000/day limit is currently a soft limit. However, the architecture must NOT rely on exceeding the free-tier limit.

Under normal operation with a 10% transient failure rate (1 retry on 10% of tasks):
`321 Initial Attempts + (32 Base Messages * 1 Retry Attempt) = 353 Delivery Attempts`

**Verdict: YELLOW**
The architecture is viable on the free tier for typical MVP loads, but aggressive retries during a Gemini rate-limit storm will easily exhaust the QStash daily quota. To mitigate this, the application must aggressively enforce caching, implement strict local idempotency, and potentially limit the QStash `max_retries` configuration to 1 or 2 attempts.
